# Agent Guide

## Project map

- This is a browser-only static application. There is no application server and no UI framework build step.
- Edit browser files in `www/`.
- `www/app.js` owns top-level application state, paper provenance, semantic-link editing, and orchestration.
- `www/db.js` owns IndexedDB schema, migrations and persistence.
- `www/graph.js` owns directed citation/topic graph rendering, cached layout, pan/zoom, pinch gestures, draggable graph items and selection callbacks.
- `www/research-relations.js` owns the canonical directed semantic relationship vocabulary between papers.
- `www/import-export.js` owns portable JSON and BibTeX parsing/serialization.
- `www/semantic-scholar.js` is an external-provider adapter; provider response shapes must be normalized before they reach the rest of the app.
- `www/pdf-ai.js` owns optional network AI PDF metadata/topic extraction.
- `www/pdf-local.js` owns the browser boundary for deterministic local Rust/WASM PDF extraction.
- `www/pdf-ai-import.js` owns the shared reviewed PDF import workflow for both local and AI extraction.
- `www/reference-resolver.js` owns exact Crossref/Semantic Scholar DOI/arXiv resolution.
- `www/reference-resolution-ui.js` integrates identifier resolution into the reviewed reference UI.
- `src/lib.rs` owns deterministic PDF text/layout parsing, bibliography detection, reference segmentation, DOI/arXiv extraction and the `wasm-bindgen` API.
- `www/pkg/` is generated by `wasm-pack`; never hand-edit or commit it.
- `www/demo-data.js` is the only bibliography data intended to be committed to the repository.
- `www/style.css`, `www/pdf-ai-import.css`, and `www/pdf-local.css` own the visual system and PDF review layout.

## Data ownership rules

- The user's live bibliography belongs in IndexedDB, never in repository files.
- Do not add user-provided papers, semantic relationships, provenance, notes, PDFs, exports or API keys to source control.
- Full database export must be schema-versioned and sufficient to restore papers, directed graph edges, topics and annotations.
- UI preferences may use localStorage, but canonical research data may not.
- Session-only graph arrangement can remain in memory unless a future explicit saved-layout feature is introduced.
- Destructive database replacement must require an explicit user action in the UI.
- The selected PDF itself is transient browser input. Do not persist PDF bytes unless a future feature explicitly introduces reviewed local file storage.

## Paper identity and duplicate rules

Use identifiers in this priority order when merging provider/import records:

1. DOI after lowercase/URL-prefix normalization.
2. Semantic Scholar paper ID.
3. arXiv identifier.
4. normalized title + publication year as a conservative fallback.

Never merge two papers solely because author lists overlap.

Preserve the original library-entry provenance when enriching an existing paper. New papers should record how they entered the library when that context is known, such as provider lookup, citation expansion, BibTeX filename, backup merge, reviewed PDF extraction, or demo data.

## Citation and research-relation semantics

- Citation edges are directed: `source` cites `target`.
- Expanding references for paper A adds edges `A -> reference`.
- Expanding citations for paper A adds edges `citingPaper -> A`.
- Expansion is user-triggered and bounded. Never recursively crawl the graph without another explicit action.
- Preserve provenance on imported/provider citation edges.
- A raw extracted bibliography entry is **not** automatically a canonical paper. Store reviewed extracted references as provenance first; create graph edges only after DOI/arXiv/provider resolution identifies a target paper.
- Semantic research relationships are **not citations**. Keep them as `kind: "research-relation"` edges with a canonical `relation` type and their own provenance.
- Canonical relation types live only in `research-relations.js`; do not duplicate ad-hoc labels in UI code.
- The same paper pair may have both a citation and semantic relationships such as `improves_on` or `outperforms`.
- Semantic relation direction matters. The detail UI may show inverse wording for incoming links but must not reverse the stored edge.

## Local PDF extraction rules

- Rust/WASM extraction is deterministic and browser-local. It must not perform network requests.
- Use `pdfplumber` from in-memory PDF bytes; do not require filesystem APIs in the WASM target.
- Bibliography detection should prefer explicit section headings. Any heuristic fallback must be conservative and expose that it was inferred.
- Reference segmentation must preserve raw citation text and page provenance.
- DOI and arXiv extraction must be normalized but must not invent missing identifiers.
- Scanned/image-only PDFs should return a clear OCR-required error rather than fabricated text.
- Every extracted reference shown to the user must remain individually reviewable before persistence.
- Keep the Rust result schema serializable through `serde-wasm-bindgen` and version it when compatibility changes.

## Topic semantics

- `topics` are research themes and may come from manual curation, provider metadata, taxonomy mapping or AI suggestions.
- `tags` are personal labels and are not automatically treated as canonical themes unless the UI explicitly promotes them.
- Local systematic citation extraction does not invent topics.
- The topic map aggregates papers into thematic blocks and preserves direction from underlying graph links.
- Future semantic/AI topic connections should be stored with a source rather than silently replacing citation-derived relationships.

## Provider rules

- Keep network-specific code inside provider modules.
- Assume rate limits and transient failures.
- Prefer pagination/batching and bounded fields.
- Never store a private provider key in source code. If a provider needs a key, it must be entered by the user and stored only locally.
- Normalize external IDs, authors, dates, URLs and citation counts before persistence.
- Provider failures must not roll back or corrupt the existing local library.

## UI and graph interaction rules

- The map is the dominant surface. Do not turn the default screen into a table-first bibliography manager.
- Keep the visual language close to Train Route Explorer: compact sticky controls, restrained colors, paper-like surfaces, dense but legible information, and purpose-specific drawers.
- Citation and Topic are peer map modes.
- Selecting a paper opens one non-modal detail drawer; do not create multiple modal layers for routine paper actions.
- Selecting/editing a paper must not restart the graph layout when the visible topology is unchanged.
- Directed graph arrows should terminate outside node/block shapes so direction remains visible.
- Paper-node citation sizing should remain modest and logarithmic rather than allowing highly cited papers to dominate the map.
- Desktop graph interaction supports background pan and wheel zoom.
- Touch/mobile graph interaction supports background pan and two-finger pinch zoom.
- Paper nodes and topic blocks are directly draggable; manually moved items remain pinned for the current application session.
- Filters and Library drawers should close when the user clicks/taps outside them.
- Reading state is strictly `unread`, `reading`, or `read`; importance belongs to relevance/star controls, not reading state.
- Search/filter interactions should update the map immediately without a manual Apply button unless a future expensive operation requires it.
- Preserve keyboard-operable controls and useful aria labels.
- Local and AI PDF analysis should converge on the same review/save interaction rather than creating parallel modal workflows.

## Performance rules

- V1 graph layout is intentionally lightweight JavaScript.
- Cache graph positions across same-topology renders; do not recompute the force simulation solely to change selection styling.
- Keep external expansion bounded and avoid loading thousands of nodes accidentally.
- When graph size starts affecting interaction, first move indexing/layout into a Web Worker.
- Rust/WebAssembly is justified for deterministic PDF parsing because it is an isolated, CPU-heavy, local-only computation with a stable input/output boundary.
- Do not move ordinary UI/state code into Rust for architectural symmetry.

## Validation sequence

At minimum after browser/Rust changes:

```bash
make test
rustup target add wasm32-unknown-unknown
make test-rust
make build-wasm
```

When the browser environment is available, also run:

```bash
make test-ui-mobile TEST_URL=http://127.0.0.1:8080/www/
```

The local citation Selenium test must exercise the generated WASM package against a real PDF fixture, not a mocked extraction object. The graph interaction Selenium test must cover mobile pinch zoom, item dragging, stable selection layout, directed edges, reading-state constraints, semantic relation creation, and provenance presentation.
